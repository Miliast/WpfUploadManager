# WPF window-open and scroll costs on .NET 8 (net8.0-windows) — mechanisms, numbers, exact fixes (state: November 2026)

Reading notes for the report writer:
- "Fetched" = I read the page itself. "Snippet" = claim comes from a search-result summary only and the page was not opened; treat as lower confidence.
- Almost all official WPF performance documentation is .NET Framework 3.x/4-era text (ms.date 2017-03-30, re-published on Learn 2025-08-27). The rendering engine (wpfgfx/milcore, DirectX 9 based) was carried over to .NET Core/.NET unchanged in architecture, so the mechanisms still apply; the absolute millisecond numbers come from ~2008-era hardware and are only useful as ratios.
- No source found in this run contains measurements of the exact constructs in the changelog window on .NET 8. Everything in "Inferences" is reasoning from the cited mechanisms and must be confirmed with a profiler (see the detection section).

## Image decoding: synchronous decode of large PNGs, DecodePixelWidth/Height, CacheOption, CreateOptions, Freeze, off-thread loading, pack:// caching, 72 dpi metadata

### Takeaway
WPF decodes every image at full pixel size by default, and Microsoft's own guidance is to "always decode the image to desired size"; for PNG and JPEG the codec decodes natively to `DecodePixelWidth`. A 72-dpi PNG is laid out at 4/3 of its pixel size (96/72), so the window's images are always being resampled, never shown 1:1.

### Cited Findings
- "By default, WPF loads your image and decodes it to its full size. If you only want a thumbnail version of the image, WPF unnecessary decodes the image to its full-size and then scales it down to a thumbnail size." Fix stated: "request WPF to decode the image to a thumbnail size". — [Optimizing Performance: 2D Graphics and Imaging (fetched)](https://learn.microsoft.com/en-us/dotnet/desktop/wpf/advanced/optimizing-performance-2d-graphics-and-imaging)
- "Always decode the image to desired size and not to the default size... You will reduce not only your application's working set, but execution speed as well." — [same page](https://learn.microsoft.com/en-us/dotnet/desktop/wpf/advanced/optimizing-performance-2d-graphics-and-imaging)
- "If possible, combine the images into a single image, such as a film strip composed of multiple images." — [same page](https://learn.microsoft.com/en-us/dotnet/desktop/wpf/advanced/optimizing-performance-2d-graphics-and-imaging)
- `BitmapImage.DecodePixelWidth`: "The width, in pixels, that the image is decoded to. The default value is 0." "If DecodePixelHeight is also set, the aspect ratio of the bitmap is ignored. If DecodePixelHeight is not set, the aspect ratio remains the same." "The JPEG and Portable Network Graphics (PNG) codecs natively decode the image to the specified size; other codecs decode the image at its original size and scale the image to the desired size." (doc applies to windowsdesktop-8.0 through 11.0) — [BitmapImage.DecodePixelWidth (fetched)](https://learn.microsoft.com/en-us/dotnet/api/system.windows.media.imaging.bitmapimage.decodepixelwidth)
- `BitmapCacheOption`: Default = OnDemand (value 0): "Creates a memory store for requested data only. The first request loads the image directly; subsequent requests are filled from the cache." OnLoad (1): "Caches the entire image into memory at load time. All requests for image data are filled from the memory store." None (2): "Do not create a memory store. All requests for the image are filled directly by the image file." — [BitmapCacheOption (fetched)](https://learn.microsoft.com/en-us/dotnet/api/system.windows.media.imaging.bitmapcacheoption)
- Off-thread pattern reported by practitioners: create the `BitmapImage` on a background thread with `CacheOption = OnLoad` (otherwise loading is lazy and happens later on first use), call `Freeze()`, then hand it to the UI thread; assigning an unfrozen bitmap across threads throws. Anecdotal counter-reports exist: one developer saw loading take "a LOT longer" after moving it to a background thread, another saw a short UI block when sources were assigned. (Snippet, Stack Overflow, not measured) — [SO: how to quickly load and display images with WPF BitmapImage](https://kiwix.lema.org/stackoverflow.com_en_all_2023-11/questions/39495099/how-to-quickly-load-and-display-images-with-wpf-bitmapimage); [SO: load a large BitmapImage asynchronously](https://kiwix.lema.org/stackoverflow.com_en_all_2023-11/questions/12825233/load-a-large-bitmapimage-asynchronously); [MS blog: SlideShow control, loading files off-thread](https://learn.microsoft.com/en-us/archive/blogs/jgalasyn/slideshow-control-loading-files-off-thread)
- DPI: WPF honours the DPI tag in the file; layout size in DIPs = pixel size x 96 / DpiX, so a 72-dpi image is 4/3 of its pixel size and is resampled even with `Stretch="None"`. Fix: re-save the PNG with 96-dpi metadata (pixels unchanged). (Snippet) — [Hanselman: Be Aware of DPI with Image PNGs in WPF](https://www.hanselman.com/blog/BeAwareOfDPIWithImagePNGsInWPFImagesScaleWeirdOrAreBlurry.aspx); [SO: why does a 72 dpi image appear bigger](https://kiwix.lema.org/stackoverflow.com_en_all_2023-11/questions/25500895/why-does-a-72-dpi-image-appear-bigger-in-96-dpi-screen); [Dwayne Need: Blurry Bitmaps](https://learn.microsoft.com/en-nz/archive/blogs/dwayneneed/blurry-bitmaps)
- .NET 10 WPF release notes mention "speeding up pixel format conversions" and a fix for "crash issues when bitmap streams are null" (no numbers). — [What's new in WPF for .NET 10 (fetched)](https://learn.microsoft.com/en-us/dotnet/desktop/wpf/whats-new/net100)

### Inferences
- Decoded size of the window's PNGs at 4 bytes/pixel: 1184x496 = 587,264 px = about 2.35 MB; 1756x960 = 1,685,760 px = about 6.74 MB per image, each decoded (PNG inflate + filter) on the UI thread when first measured/rendered because XAML `Source="pack://..."` creates a `BitmapImage` with default (lazy, OnDemand) options. (Arithmetic; the UI-thread claim follows from the lazy-load statements above, not from a measurement.)
- With 72-dpi metadata the natural DIP sizes are about 1579x661 and 2341x1280, so `StretchDirection="DownOnly"` always downsizes; the HighQuality (Fant) scaler therefore always runs (see next section).
- For the 26x18 thumbnail and the 302x136 preview, a separate `BitmapImage` with `DecodePixelWidth` (thumbnail: about 2x target, e.g. 52-104 px; preview: 302 x DPI scale) removes both the full decode and the large-ratio Fant downscale. `DecodePixelWidth` is in physical pixels, so multiply by the monitor DPI scale (150 % -> x1.5).
- Exact fix pattern (not benchmarked here): `var bi = new BitmapImage(); bi.BeginInit(); bi.UriSource = packUri; bi.DecodePixelWidth = n; bi.CacheOption = BitmapCacheOption.OnLoad; bi.EndInit(); bi.Freeze();` executed in `Task.Run`, result assigned on the UI thread; or pre-scale the PNG assets at build time and ship 96-dpi files.

### Gaps
- No source found with measured PNG decode times for these sizes on .NET 8; expectation of "tens of ms per image" is unverified.
- How WPF caches `pack://` images (the internal weak-reference image cache keyed by URI, and `BitmapCreateOptions.IgnoreImageCache`) was not confirmed from a source in this run. Whether the same URI used in an `Image` and in an `ImageBrush` shares one decode is therefore unverified.
- Whether `DecodePixelWidth` alters the reported DPI/DIP size of a 72-dpi source was not verified.
- `BitmapCreateOptions` (DelayCreation, PreservePixelFormat) semantics were not fetched.

## RenderOptions.BitmapScalingMode: cost of HighQuality/Fant versus Linear/LowQuality

### Takeaway
`HighQuality` is literally the same enum value as `Fant` (2) and is documented as "slower than all other bitmap scaling modes"; a WPF graphics team member states Fant "is done on the CPU at certain intervals" while Linear "is done entirely by the GPU". The default since .NET 4 is Linear, so the window has explicitly opted into the CPU path for every image and image brush.

### Cited Findings
- Enum table: `Unspecified` = 0 "Use the default bitmap scaling mode, which is Linear"; `Linear` = 1; `LowQuality` = 1 "The LowQuality mode is the same as the Linear mode"; `Fant` = 2 "very high quality Fant bitmap scaling, which is slower than all other bitmap scaling modes"; `HighQuality` = 2 "The HighQuality mode is the same as the Fant mode"; `NearestNeighbor` = 3 "provides performance benefits over LowQuality mode when the software rasterizer is used". — [BitmapScalingMode Enum (fetched, covers windowsdesktop-8.0..11.0)](https://learn.microsoft.com/en-us/dotnet/api/system.windows.media.bitmapscalingmode)
- "Fant produces the best looking scaled bitmap but the scaling is done on the CPU at certain intervals. This CPU usage can make your scale animations stutter. On the other hand, Linear is done entirely by the GPU so everything is smooth but the quality suffers. Linear may also use more video memory than Fant but that depends on the scenario." (Jordan, WPF 3D team, 26 May 2010) — [.NET 4.0 Image Scaling Change Reminder (fetched)](https://learn.microsoft.com/en-us/archive/blogs/wpf3d/net-4-0-image-scaling-change-reminder)
- ".NET 4: The default RenderOptions.BitmapScalingMode default is now changed Linear instead of Fant. This should provide some perf improvement if you scale images." — [What's New for Performance in WPF in .NET 4 (fetched)](https://learn.microsoft.com/en-us/archive/blogs/jgoldb/whats-new-for-performance-in-wpf-in-net-4)
- "When animating the scale of any bitmap, the default high-quality image resampling algorithm can sometimes consume sufficient system resources to cause frame rate degradation... By setting the BitmapScalingMode property ... to LowQuality, you can create a smoother animation when scaling a bitmap." (Note: the phrase "default high-quality" is stale pre-.NET 4 wording; the same page's enum table says the default is Linear.) — [Optimizing Performance: 2D Graphics and Imaging](https://learn.microsoft.com/en-us/dotnet/desktop/wpf/advanced/optimizing-performance-2d-graphics-and-imaging); [BitmapScalingMode Enum](https://learn.microsoft.com/en-us/dotnet/api/system.windows.media.bitmapscalingmode)
- `RenderOptions` are attached properties that do not work on every object: "BitmapScalingMode needs to be set on a UIElement or, I think, DrawingGroup. It inherits." (same author, comment, 2010) — [.NET 4.0 Image Scaling Change Reminder](https://learn.microsoft.com/en-us/archive/blogs/wpf3d/net-4-0-image-scaling-change-reminder)
- "RenderOptions and TextOptions do not propagate through a cached element [BitmapCache]. You may have to set these options again in child elements below the cache." — [BitmapCache Class (fetched)](https://learn.microsoft.com/en-us/dotnet/api/system.windows.media.bitmapcache)

### Inferences
- "At certain intervals" plus the documented stutter only during *scale animations* implies the Fant result is cached per (bitmap, target size) and recomputed when the effective scale changes, not on every composed frame. Plain translation while scrolling should then reuse the cached result; anything that changes the scale re-runs the CPU resampler.
- This matters for the window's scroll handler: it assigns `ScaleTransform` objects to `RenderTransform` on rows. If the scaled rows contain HighQuality images/brushes, every scroll tick changes the effective bitmap scale and can trigger a CPU Fant resample of a 1.7-megapixel source. This is the single most plausible "HighQuality makes scrolling slow" mechanism in this window, and it is unverified.
- Fant cost grows with source pixel count, so the worst case is the 1756x960 PNG feeding the 26x18 thumbnail (about 3,600:1 pixel reduction on the CPU). Decoding the thumbnail at small size removes this entirely and makes the scaling mode irrelevant for it.
- Practical lever: pre-size the bitmap (`DecodePixelWidth`) so the on-screen scale is near 1:1 and drop `HighQuality` (Linear on the GPU is then visually close); keep `HighQuality` only on the one large hero image if the quality difference is visible, and never on elements whose scale is animated.

### Gaps
- No Microsoft statement found on exactly when Fant output is cached/invalidated, nor any timing for Fant on megapixel sources. The 2010 statement is the only primary description found.
- Whether `ImageBrush` with `HighQuality` (set on the Ellipse/Border that owns the brush) follows the same cached path as `Image` was not confirmed.

## OpacityMask with VisualBrush, and cheaper rounded image corners

### Takeaway
A WPF team blog ranks the three ways to round an image's corners by cost: "Rectangle/Image Brush < Clipping < Opacity Mask", and Microsoft documents that a VisualBrush's content is by default "re-render[ed] ... for every frame, even though the content is unchanging". The VisualBrush OpacityMask is therefore the most expensive of the available options, applied to the largest bitmaps in the window.

### Cited Findings
- "Option 1: (recommended, most performant) Draw a Rectangle with Rounded Corners and Fill it with the ImageBrush"; Option 2: a clipping path (`UIElement.Clip = new RectangleGeometry(rect, rx, ry)` updated in `SizeChanged`); Option 3: OpacityMask. "Rectangle/Image Brush < Clipping < Opacity Mask for how expensive it will be." "On performance, differences should not be too noticeable unless you do it 100s of times ... but if you do it many times (e.g. image catalog) it will add-up." (Jaime Rodriguez, Microsoft, 8 June 2006) — [rounded corner images in wpf (fetched)](https://learn.microsoft.com/en-nz/archive/blogs/jaimer/rounded-corner-images-in-wpf)
- "in earlier builds, and I think still in beta2- OpacityMasks forced software rendering. no worries it is fixed in later builds... now that OpacityMask is hardware accelerated it is also not a huge deal to use it". So OpacityMask itself does not force software rendering in released WPF. — [same post](https://learn.microsoft.com/en-nz/archive/blogs/jaimer/rounded-corner-images-in-wpf)
- "By default, WPF does not cache the rendered contents of TileBrush objects, such as DrawingBrush and VisualBrush... The default behavior of WPF is to re-render the entire content of the DrawingBrush or VisualBrush for every frame, even though the content is unchanging." Fix: `RenderOptions.SetCachingHint(brush, CachingHint.Cache)` plus `CacheInvalidationThresholdMinimum` / `CacheInvalidationThresholdMaximum` (e.g. 0.5 / 2.0: regenerate only when the size is half or double the cached size). — [Optimizing Performance: 2D Graphics and Imaging (fetched)](https://learn.microsoft.com/en-us/dotnet/desktop/wpf/advanced/optimizing-performance-2d-graphics-and-imaging)
- Not hardware accelerated: "Tiled content that uses TileBrush — Any tiled content in which the TileMode property of the TileBrush is set to Tile." (An untiled VisualBrush, TileMode=None, is not in this list.) — [Graphics Rendering Tiers (fetched)](https://learn.microsoft.com/en-us/dotnet/desktop/wpf/advanced/graphics-rendering-tiers)
- Anecdotal problems with VisualBrush masks: wrong viewport when content is rotated or has margins; a report of large memory use traced to VisualBrush objects held by an OpacityMask. (Snippet) — [SO: WPF VisualBrush and OpacityMask](https://kiwix.lema.org/stackoverflow.com_en_all_2023-11/questions/1941508/c-wpf-visualbrush-and-opacitymask); [SO: Border with OpacityMask VisualBrush memory leaks](https://kiwix.lema.org/stackoverflow.com_en_all_2023-11/questions/6269522/wpf-border-with-a-opacitymask-visualbrush-memory-leaks)

### Inferences
- An OpacityMask needs the element rendered to an off-screen surface plus the mask rendered to a second surface, then blended; with a VisualBrush the mask surface is produced by rendering a live visual (the rounded Border) and, per the CachingHint text, is regenerated each frame unless cached. For the 1756x960 image this is two large intermediate surfaces per image. (Mechanism inferred; the docs state the re-render but not the surface count.)
- Because the window already uses `ImageBrush` in Ellipses elsewhere, the cheapest consistent replacement is a `Border CornerRadius="r"` (or `Rectangle RadiusX/RadiusY`) whose `Background`/`Fill` is an `ImageBrush Stretch="Uniform"`; this is the option the Microsoft post calls "most performant". Sizing must then come from the container, since a brush does not give the element a natural size.
- If an `Image` element must stay (for `StretchDirection="DownOnly"` natural sizing), set `Image.Clip` to a frozen `RectangleGeometry` with `RadiusX/RadiusY`, updated on `SizeChanged`; second cheapest per the same ranking.
- If the VisualBrush mask is kept, `RenderOptions.CachingHint="Cache"` on the brush is the documented mitigation.

### Gaps
- No .NET-era benchmark of OpacityMask(VisualBrush) versus Clip versus ImageBrush was found; the ranking is a 2006 qualitative statement from a Microsoft employee.
- Whether `Opacity` animations on a subtree containing masked images compound the intermediate-surface cost was not sourced.

## Effects: BlurEffect and DropShadowEffect — hardware acceleration, cost versus radius and size, cheaper shadows

### Takeaway
`BlurEffect` and `DropShadowEffect` are pixel-shader effects that are hardware accelerated on a Tier-2 GPU, with a measured "~5x" gain over the old software path, but they are per-pixel operations over the whole affected element; in software rendering they run on the CPU. No source quantifies cost versus radius; the only documented knob is `RenderingBias` (default `Performance`).

### Cited Findings
- .NET 3.5 SP1: "the Blur and DropShadow BitmapEffects are Hardware Accelerated and rendered by the GPU. We measured ~5x CPU, frame rate and video memory usage gains in by using the GPU for some scenarios." "New Effects (now called BlurEffect, DropShadowEffect) are introduced and these will always be Hardware Accelerated." Legacy path gets no gain when effects "Have too large a blur radius" or "Aren't running on a Tier-2 video card (DX Ver. >= 9.0)". — [What's New for Performance in WPF in .NET 3.5 SP1 (fetched, 15 May 2008)](https://learn.microsoft.com/en-us/archive/blogs/jgoldb/whats-new-for-performance-in-wpf-in-net-3-5-sp1)
- "A pixel shader is a graphics processing function that calculates effects on a per-pixel basis. Depending on the resolution of the displayed graphics, there could be several million pixels that need to be processed for each display frame." — [Graphics Rendering Tiers](https://learn.microsoft.com/en-us/dotnet/desktop/wpf/advanced/graphics-rendering-tiers)
- `RenderCapability.IsPixelShaderVersionSupported(major, minor)` tells whether shader effects run in hardware; `RenderCapability.IsShaderEffectSoftwareRenderingSupported` indicates "whether the system supports SSE2 and where the HLSL 'JIT' will work" (i.e. effects have a CPU fallback). — [.NET 3.5 SP1 post](https://learn.microsoft.com/en-us/archive/blogs/jgoldb/whats-new-for-performance-in-wpf-in-net-3-5-sp1)
- .NET 4: "Pixel Shader 2.0 is now required for hardware acceleration." Legacy `BitmapEffect` classes "are now no-ops". — [What's New for Performance in WPF in .NET 4](https://learn.microsoft.com/en-us/archive/blogs/jgoldb/whats-new-for-performance-in-wpf-in-net-4)
- `DropShadowEffect.RenderingBias` / `BlurEffect.RenderingBias`: "indicates whether the system renders the drop shadow with emphasis on speed or quality. The default is Performance." (Snippet) — [DropShadowEffect.RenderingBias](https://msdn.microsoft.com/en-us/library/system.windows.media.effects.dropshadoweffect.renderingbias.aspx)
- "Changes to the parent visual tree of the cached UIElement, such as transforms, scales, opacities, and effects, do not affect the cache." (i.e. an element with `CacheMode=BitmapCache` under an effect is not re-rasterized when the effect above it changes.) — [BitmapCache Class](https://learn.microsoft.com/en-us/dotnet/api/system.windows.media.bitmapcache)
- Software pipeline: "The biggest performance issue you will encounter when rendering in software mode is related to fill rate, which is defined as the number of pixels that you are rendering." — [Optimizing Performance: Taking Advantage of Hardware (fetched)](https://learn.microsoft.com/en-us/dotnet/desktop/wpf/advanced/optimizing-performance-taking-advantage-of-hardware)
- Community guidance (MaterialDesignInXaml docs PR): avoid DropShadowEffect/BlurEffect where possible "as these can slow down rendering"; a Stack Overflow thread reports a drop shadow making animations less smooth. (Snippet, anecdotal) — [MaterialDesignInXamlToolkit PR 3709](https://github.com/MaterialDesignInXAML/MaterialDesignInXamlToolkit/pull/3709/files); [SO: WPF animation UI features performance](https://kiwix.lema.org/stackoverflow.com_en_all_2023-11/questions/961875/wpf-animation-ui-features-performance-and-benchmarking)

### Inferences
- An Effect on an element forces that element's whole subtree to be rasterized into an intermediate texture, which the shader then processes. With `BlurEffect` on the ScrollViewer, every frame in which anything inside changes (every scroll tick, every opacity animation frame, every hover) re-rasterizes the entire viewport subtree into the intermediate and re-runs the blur; while `Radius` is animated the blur shader runs each frame over the full ScrollViewer area. Mechanism is standard WPF behaviour but was not confirmed from a source in this run.
- If the BlurEffect object stays attached with `Radius=0` after the animation, the intermediate surface pass very likely remains; set `Effect = null` when the animation completes (and only attach it when the blur starts).
- For the entrance blur, the cached-composition statement above suggests the cheap variant: put `CacheMode="BitmapCache"` on the content *below* the blurred element so the blur consumes a cached bitmap instead of re-rendering text, paths and images each frame; remove the cache afterwards if the content must stay crisp at all DPI scales.
- `DropShadowEffect` with BlurRadius 40-80 on a panel that *contains* the scrolling content makes the shadow recompute over the whole panel area on every content change. Cheaper equivalents that keep the look: (a) apply the effect to an empty sibling `Border` of the same size/CornerRadius placed behind the panel (its subtree never changes, so the shadow is rendered once); (b) a pre-rendered 9-slice shadow PNG; (c) stacked semi-transparent Borders or a gradient brush. For the ToolTip, the shadow forces a layered popup window (see next section).
- The user's "soft, wide glow" preference is compatible with (a) and (b); neither changes the visual result.

### Gaps
- No source gives cost as a function of blur radius or element area, on .NET 8 or otherwise; "~5x" is a 2008 hardware-versus-software number for unspecified scenarios.
- Not confirmed from a primary source: that an attached effect with Radius 0 still costs an intermediate pass; that `RenderingBias.Quality` on .NET 8 changes the shader pass count.
- No dotnet/wpf issue was found documenting DropShadowEffect falling back to software on .NET 8 for large radii.

## AllowsTransparency / layered windows (popups, tooltips with drop shadow)

### Takeaway
Layered windows are hardware accelerated on WDDM systems (Vista and later), but they are listed among the features with special handling and historically cost a GPU readback; on non-WDDM systems they are software rendered. ToolTips and Popups that have transparency are layered windows.

### Cited Findings
- "Layered windows allow WPF applications to render content to the screen in a non-rectangular window. On operating systems that support Windows Display Driver Model (WDDM), such as Windows Vista and Windows 7, layered windows are hardware accelerated. On other systems, such as Windows XP, layered windows are rendered by software with no hardware acceleration." Enabled by `WindowStyle=None`, `AllowsTransparency=true`, `Background=Transparent`. — [Graphics Rendering Tiers](https://learn.microsoft.com/en-us/dotnet/desktop/wpf/advanced/graphics-rendering-tiers)
- Layered-window fixes shipped in XP SP3 / Vista SP1: "On XP: Huge improvements as now render in HW vs. SW before. On Vista: Smaller but still significant improvement to readback from GPU". — [.NET 3.5 SP1 performance post](https://learn.microsoft.com/en-us/archive/blogs/jgoldb/whats-new-for-performance-in-wpf-in-net-3-5-sp1)
- "depending on the machine configuration and the application, software-based rendering is sometimes faster than hardware" (stated in the context of layered windows; links to a post titled "layered windows: SW is sometimes faster than HW"). — [.NET 4 performance post](https://learn.microsoft.com/en-us/archive/blogs/jgoldb/whats-new-for-performance-in-wpf-in-net-4)

### Inferences
- The "readback from GPU" wording means a layered WPF window renders on the GPU and then copies the pixels back to system memory for `UpdateLayeredWindow`; cost scales with window pixel area per frame. A tooltip is small, so the custom ToolTip with a shadow is a minor cost; a full-size dialog with `AllowsTransparency=True` would pay this on every frame of every animation and scroll. The brief does not say whether the changelog window itself is transparent; if it is, that is a first-order lever (use `WindowChrome` with an opaque window instead).

### Gaps
- No current (Windows 10/11, .NET 8) measurement of layered-window overhead was found; the cited statements are 2008-2010.
- Whether the changelog window uses `AllowsTransparency` is unknown to this researcher.

## Software rendering fallback: when it happens, how to detect it, how bad it is

### Takeaway
WPF silently renders in software under RDP (default), on Tier-0 hardware, in some VMs, when the window exceeds the max texture size, after out-of-video-memory, and for specific features; in that mode everything, including effects and bitmap scaling, is CPU fill-rate bound. Detection: `RenderCapability.Tier >> 16`, `RenderOptions.ProcessRenderMode`, and Perforator's purple tint. .NET 8 added an opt-in switch for hardware acceleration over RDP.

### Cited Findings
- List of software-rendering triggers (22 June 2010): old video driver (before 11/2004); Tier 0 card; "The rendered Window's size exceeds the max video card texture size" (e.g. spanning monitors); "You run your application over Remote Desktop Protocol... WPF renders the application content using a software rasterizer on the server and then remotes the content as bitmaps in all cases"; "Rendering in Virtual Machine. WPF will try and render in HW but on some VMs the graphic emulator that comes with the VM is not working correctly"; forced via `RenderOptions.ProcessRenderMode = RenderMode.SoftwareOnly` or `HwndTarget.RenderMode`; `DisableHWAcceleration` registry key; printed content; `RenderTargetBitmap`; tiled `TileBrush`; too many 3D lights; layered windows on pre-hotfix XP; "Graphics hardware failures, such as 'Out Of Video Memory'". — [Software Rendering Usage in WPF (fetched)](https://learn.microsoft.com/en-us/archive/blogs/jgoldb/software-rendering-usage-in-wpf)
- Tier definitions (current): Tier 0 "No graphics hardware acceleration. All graphics features use software rendering"; Tier 1 and 2 require DirectX >= 9.0 and pixel shader >= 2.0; video RAM >= 60 MB (Tier 1) / >= 120 MB (Tier 2); Tier 2 also needs vertex shader 2.0 and 4 multitexture units. "For most graphics hardware, large surfaces are 2048x2048 or 4096x4096 pixels in size." — [Graphics Rendering Tiers](https://learn.microsoft.com/en-us/dotnet/desktop/wpf/advanced/graphics-rendering-tiers)
- Conflict between official pages: the "Taking Advantage of Hardware" page still describes Tier 1 as DirectX 7.0 to below 9.0 and Tier 0 as below 7.0; the "Graphics Rendering Tiers" page notes "Starting in the .NET Framework 4, rendering tier 1 has been redefined to only include graphics hardware that supports DirectX 9.0 or greater." The latter is the current definition. — [Taking Advantage of Hardware](https://learn.microsoft.com/en-us/dotnet/desktop/wpf/advanced/optimizing-performance-taking-advantage-of-hardware); [Graphics Rendering Tiers](https://learn.microsoft.com/en-us/dotnet/desktop/wpf/advanced/graphics-rendering-tiers)
- "The WPF software rendering pipeline is entirely CPU bound... if you have an application with a blue background, which then renders a slightly transparent image over it, you will render all of the pixels in the application twice. As a result, it will take twice as long". — [Taking Advantage of Hardware](https://learn.microsoft.com/en-us/dotnet/desktop/wpf/advanced/optimizing-performance-taking-advantage-of-hardware)
- Detection: Perforator (WPF Performance Suite) option "Draw software rendering with purple tint: Draws all areas rendered by using the software rendering pipeline with a purple tint. This includes software render targets, software 3D content, and per-primitive software fallback." In code: check `RenderCapability.Tier` and the `TierChanged` event. — [Software Rendering Usage in WPF](https://learn.microsoft.com/en-us/archive/blogs/jgoldb/software-rendering-usage-in-wpf)
- Precedence of software forcing: registry key, then `RenderOptions.ProcessRenderMode`, then `HwndTarget.RenderMode`; "there is no way to force Hardware rendering back on once it was set to SoftwareOnly." Visual Studio 2010 forced software rendering on VMs "since some VMs graphic emulation drivers found not to be reliable". — [.NET 4 performance post](https://learn.microsoft.com/en-us/archive/blogs/jgoldb/whats-new-for-performance-in-wpf-in-net-4)
- "Remote Desktop always yields render tier 0" (WPF 3D team blog; snippet). — [D3DImage and software rendering](https://learn.microsoft.com/en-us/archive/blogs/wpf3d/d3dimage-and-software-rendering)
- .NET 8: "Previously, all WPF applications that were accessed remotely had to use software rendering, even if the system had hardware rendering capabilities"; .NET 8 adds an opt-in via runtimeconfig property `Switch.System.Windows.Media.EnableHardwareAccelerationInRdp` = true (no MSBuild property; not settable through `DOTNET_` environment variables; can be set through a `RuntimeHostConfigurationOption` item). ### Inferences
- The project is developed on macOS (darwin), so the app is almost certainly being run in a Windows VM (Parallels/VMware on Apple Silicon, i.e. Windows on ARM with a virtual display adapter) or over a remote session. That is exactly the environment where WPF either falls back to software or runs on a weak virtual GPU. In software mode a Radius-18 blur over the whole ScrollViewer and 40-80 px shadows are computed on the CPU for every changed frame, which alone could explain both the slow open and the slow scroll. First diagnostic step before any optimisation: log `RenderCapability.Tier >> 16` (0 = software, 2 = full hardware), `RenderCapability.IsPixelShaderVersionSupported(2, 0)`, and `SystemParameters.IsRemoteSession` at window open, on the slow machine and on a real PC.
- If the tier is 0 in the VM, measurements taken there do not represent end-user hardware; conversely, if end users run under RDP/Citrix, the effect-heavy design needs a reduced-effects path (check tier, skip BlurEffect/DropShadowEffect).

### Gaps
- No source found on WPF rendering tier/behaviour specifically under Parallels, VMware Fusion, or Windows-on-ARM x64 emulation; the VM statement is from 2010.
- WPF Perforator dates from the Windows SDK 7.x era; whether it attaches cleanly to .NET 8 processes was not verified. Alternatives (Visual Studio Application Timeline / PerfView / ETW provider `Microsoft-Windows-WPF`) were not researched in this run.

## XAML/BAML load, ResourceDictionaries, StaticResource versus DynamicResource, Path geometry, freezing

### Takeaway
Microsoft's guidance, with numbers: share resources at Window/Application level, prefer StaticResource (DynamicResource "imposes a performance impact"), freeze Freezables (frozen SolidColorBrush 212 bytes versus 972 bytes unfrozen when shared by ten elements), and prefer Drawing objects over Shape elements because each `Path` is a full FrameworkElement. `Path Data="..."` mini-language already produces a `StreamGeometry`. The geometry/BAML parsers were micro-optimised in .NET 7 and XAML parsing again in .NET 10.

### Cited Findings
- "Drawing objects are simpler constructs than Shape objects and provide better performance characteristics." "Since Shape objects derive from the FrameworkElement class, using them can add significantly more memory consumption in your application. If you really do not need the FrameworkElement features for your graphical content, consider using the lighter-weight Drawing objects." — [Optimizing Performance: 2D Graphics and Imaging](https://learn.microsoft.com/en-us/dotnet/desktop/wpf/advanced/optimizing-performance-2d-graphics-and-imaging)
- "The StreamGeometry object is a lightweight alternative to PathGeometry... StreamGeometry is optimized for handling many PathGeometry objects and performs better when compared to using many individual PathGeometry objects." The doc's StreamGeometry example is the attribute syntax `<Path Data="F0 M10,100 L100,100 100,50Z" .../>`, i.e. path mini-language in an attribute yields a StreamGeometry. — [same page](https://learn.microsoft.com/en-us/dotnet/desktop/wpf/advanced/optimizing-performance-2d-graphics-and-imaging)
- "The DrawingVisual object is a lightweight drawing class... does not provide layout or event handling, which improves its performance. For this reason, drawings are ideal for backgrounds and clip art." — [same page](https://learn.microsoft.com/en-us/dotnet/desktop/wpf/advanced/optimizing-performance-2d-graphics-and-imaging)
- "Freezing objects whenever possible improves the performance of your application and reduces its working set." Frozen SolidColorBrush 212 bytes versus non-frozen 972 bytes (one brush applied to ten Rectangles); unfrozen brushes keep a Changed handler per consumer, and "change notifications are costly". — [Optimizing Performance: Object Behavior (fetched)](https://learn.microsoft.com/en-us/dotnet/desktop/wpf/advanced/optimizing-performance-object-behavior)
- "A dynamic resource ... will create a temporary expression during the initial compilation and thus defer lookup ... Lookup behavior for that resource is analogous to run-time lookup, which imposes a performance impact. Use static resources whenever possible". — [Optimizing Performance: Application Resources (fetched)](https://learn.microsoft.com/en-us/dotnet/desktop/wpf/advanced/optimizing-performance-application-resources)
- "define the brush as a resource and reference it, rather than defining the brush inline in XAML. This method will create one instance and reuse it, whereas defining brushes inline in XAML creates a new instance for each element." Resources defined inside a repeated control's own ResourceDictionary are instantiated per instance (52 x 52 brushes example). — [same page](https://learn.microsoft.com/en-us/dotnet/desktop/wpf/advanced/optimizing-performance-application-resources)
- "If you haven't optimized your control templates, you may be creating a lot of extra unnecessary objects in the visual tree." — [Optimize control performance (fetched)](https://learn.microsoft.com/en-us/dotnet/desktop/wpf/advanced/optimizing-performance-controls)
- Tree construction order: 150-level tree built bottom-up 366 ms (454 ms incl. render) versus top-down 11 ms (96 ms). "When a node is added or removed from the logical tree, property invalidations are raised on the node's parent and all its children." — [Optimizing Performance: Layout and Design (fetched)](https://learn.microsoft.com/en-us/dotnet/desktop/wpf/advanced/optimizing-performance-layout-and-design)
- .NET 7 parser work (inherited by .NET 8): "Small performance improvement of PathParser"; "Use span slice instead of substring in AbbreviatedGeometryParser.ReadNumber"; "Avoid unnecessary byte[] allocation in Baml2006Reader.Process_Header"; "Remove substring allocation from Baml2006Reader.Logic_GetFullXmlns"; "Avoid exceptional string allocation in StaticExtension.ProvideValue"; "Avoid boxing when setting DependencyObject properties". No timings published. — [What's new for WPF in .NET 7](https://devblogs.microsoft.com/dotnet/wpf-on-dotnet-7/)
- .NET 10: performance "optimized across ... dynamic resources ... and XAML parsing". — [What's new in WPF for .NET 10](https://learn.microsoft.com/en-us/dotnet/desktop/wpf/whats-new/net100)
- .NET 4 (historical): "WPF designer template parsing is now about 2x faster"; "Performance of loading loose XAML significantly improved." — [.NET 4 performance post](https://learn.microsoft.com/en-us/archive/blogs/jgoldb/whats-new-for-performance-in-wpf-in-net-4)

### Inferences
- Parsing about 10 KB of path mini-language is small in absolute terms (it is a tight tokenizer loop; .NET 7 removed its substring allocations); the larger cost of a dozen `<Path>` elements is a dozen FrameworkElements (style lookup, measure/arrange, per-element render data) and, with anti-aliased Béziers, GPU tessellation on every re-render. Collapsing the illustration into one `DrawingImage`/`DrawingGroup` of `GeometryDrawing`s held as a frozen resource (`po:Freeze="True"` with `xmlns:po="http://schemas.microsoft.com/winfx/2006/xaml/presentation/options"`) reduces it to one element, and adding `CacheMode="BitmapCache"` to that one element makes it scroll as a single textured quad (see BitmapCache section). This fits the "few files, XAML + code-behind" preference.
- DataTemplate content is instantiated per item from the BAML template record, so "many StaticResource lookups" are paid per row, per property, at instantiation (a dictionary walk up the tree to the window/app resources); they are cheap individually. Converters and DataTriggers run per row at load. For a dozen rows none of this is likely to dominate compared with image decode, effects and fonts; confirm with a profiler before restructuring templates.
- Brushes, Pens, Geometries, Transforms, TextDecorations and BitmapImages declared in the window's resources should all be frozen; anything animated or mutated (the scroll-handler transforms) must stay unfrozen.
- The reflection-based System.Text.Json read in the window constructor is outside WPF but sits on the same critical path: first-use reflection metadata generation and JIT of the serializer happen on the UI thread before the first frame. Source-generated `JsonSerializerContext` or loading the JSON before/after first render are the usual levers (not researched here; another researcher may cover it).

### Gaps
- No published timing for BAML load of a window of this size on .NET 8, for StaticResource versus DynamicResource lookup, or for Path-string parsing per KB.
- No measurement comparing N Path elements versus one DrawingImage on .NET 8.
- ReadyToRun/TieredPGO effects on first-open JIT cost of WPF code were out of scope for this run and not researched.

## Layout: non-virtualized ItemsControl in a ScrollViewer, VirtualizingStackPanel, pixel scrolling, deferred loading

### Takeaway
Virtualization pays off by orders of magnitude at thousands of items (3210 ms versus 46 ms for 5000 TextBlocks) but for about a dozen heavy rows the lever is deferring off-screen row content, not the panel type. A plain `ItemsControl` does not virtualize unless its `ItemsPanel` is a `VirtualizingStackPanel`, `IsVirtualizing` is true, and scrolling stays content-based.

### Cited Findings
- 5000 TextBlocks, time from setting ItemsSource to display: StackPanel 3210 ms; VirtualizingStackPanel 46 ms. — [Optimizing Performance: Object Behavior](https://learn.microsoft.com/en-us/dotnet/desktop/wpf/advanced/optimizing-performance-object-behavior)
- "By default, UI virtualization is enabled for the ListView and ListBox controls when their list items are bound to data." For ItemsControl-derived controls "you can set the ItemsPanel to VirtualizingStackPanel and set IsVirtualizing to true." Conditions that disable virtualization: item containers added directly; item containers of different types; "Setting CanContentScroll to false"; "Setting IsVirtualizing to false". — [Optimize control performance](https://learn.microsoft.com/en-us/dotnet/desktop/wpf/advanced/optimizing-performance-controls)
- Container recycling: `VirtualizingPanel.VirtualizationMode="Recycling"`; "up to 40% scroll performance improvement in the basic case". — [Optimize control performance](https://learn.microsoft.com/en-us/dotnet/desktop/wpf/advanced/optimizing-performance-controls); [.NET 3.5 SP1 performance post](https://learn.microsoft.com/en-us/archive/blogs/jgoldb/whats-new-for-performance-in-wpf-in-net-3-5-sp1)
- Deferred scrolling: `ScrollViewer.IsDeferredScrollingEnabled="True"` updates content only when the thumb is released. — [Optimize control performance](https://learn.microsoft.com/en-us/dotnet/desktop/wpf/advanced/optimizing-performance-controls)
- With virtualization on, `VirtualizingPanel.ScrollUnit` (Pixel or Item) governs scrolling granularity instead of forcing `CanContentScroll=False`; Pixel gives smooth scrolling while keeping virtualization. (Snippet; secondary Chinese-language blogs, not official docs) — [WPF list virtualization scrolling modes](https://www.cnblogs.com/kybs0/p/7649463.html)
- "The layout pass is a mathematically-intensive process—the larger the number of children in the collection, the greater the number of calculations required." Layout is re-invoked when a child is added, a `LayoutTransform` is applied, `UpdateLayout` is called, or a measure/arrange-affecting dependency property changes. — [Optimizing Performance: Layout and Design](https://learn.microsoft.com/en-us/dotnet/desktop/wpf/advanced/optimizing-performance-layout-and-design)
- Scrolling without re-rasterization: with cached composition WPF can "create a smooth scroll experience that scrolls cached images ... of live content that doesn't have to be re-rendered every frame." — [.NET 4 performance post](https://learn.microsoft.com/en-us/archive/blogs/jgoldb/whats-new-for-performance-in-wpf-in-net-4)

### Inferences
- An `ItemsControl` whose template has no ScrollViewer, placed inside an outer `ScrollViewer`, is measured with infinite height, so all rows are created, measured, arranged and rendered at window open, including every off-screen image decode. With roughly a dozen changelog entries the container/layout cost is small; the cost is what each row drags in (megapixel PNG decode, Fant scale, VisualBrush mask, fonts).
- Two WPF-specific ways to defer that: (a) real virtualization: give the ItemsControl a template `ScrollViewer(CanContentScroll=True) > ItemsPresenter`, `ItemsPanel = VirtualizingStackPanel`, `VirtualizingPanel.IsVirtualizing="True"`, `VirtualizingPanel.ScrollUnit="Pixel"`, `VirtualizingPanel.CacheLength="1"` with `CacheLengthUnit="Page"`; (b) keep the simple panel but lazy-load only the expensive parts: bind image sources to a property that is filled asynchronously after first render (`Dispatcher.BeginInvoke(DispatcherPriority.ContextIdle / Background)` or off-thread decode), newest/visible entries first.
- Option (a) conflicts with the existing scroll handler, which assumes every container exists (`ContainerFromIndex` returns null for virtualized rows) and with per-row parallax transforms; option (b) keeps the current structure and is the lower-risk change for a short list.
- `UseLayoutRounding=True` adds rounding work per element during arrange; negligible relative to the items above (not sourced).

### Gaps
- No source defines a threshold at which a non-virtualized ItemsControl "starts to matter"; the 5000-item figure is the only official number.
- `VirtualizingPanel.ScrollUnit`/`CacheLength` statements come from secondary sources and API knowledge; the official API pages were not fetched in this run.
- Cost of `ShowDialog()` itself (nested message pump, owner disable) versus `Show()`: nothing found; no evidence that it contributes measurably.

## Scroll handler: TranslatePoint/FindName per event, allocating transforms, better patterns

### Takeaway
Microsoft's explicit guidance is "Update Rather than Replace a RenderTransform". The handler described replaces transforms on every scroll event and performs per-row tree walks; the documented pattern is one long-lived, unfrozen transform per row whose properties are mutated.

### Cited Findings
- "You may be able to update a Transform rather than replacing it as the value of a RenderTransform property. This is particularly true in scenarios that involve animation. By updating an existing Transform, you avoid initiating an unnecessary layout calculation." — [Optimizing Performance: Layout and Design](https://learn.microsoft.com/en-us/dotnet/desktop/wpf/advanced/optimizing-performance-layout-and-design)
- Layout is forced by `UpdateLayout` and by `LayoutTransform`; `RenderTransform` is not in the list of layout triggers. — [same page](https://learn.microsoft.com/en-us/dotnet/desktop/wpf/advanced/optimizing-performance-layout-and-design)
- Unfrozen Freezables assigned to a dependency property get a Changed handler pointing back at the element ("a delegate pointing back to the Rectangle object will be added to the SolidColorBrush object's Changed event"); adding/removing such handlers is "very performance intensive". — [Optimizing Performance: Object Behavior](https://learn.microsoft.com/en-us/dotnet/desktop/wpf/advanced/optimizing-performance-object-behavior)
- "Without this caching, simply animating an otherwise static element across the screen forces that element to be repeatedly be completely re-tessellated and re-rasterized ... This often leaves WPF's rendering pipeline bottlenecked in CPU-bound per-primitive setup cost." Transforms and opacities applied above a cached element "do not force the cache to be regenerated". — [.NET 4 performance post](https://learn.microsoft.com/en-us/archive/blogs/jgoldb/whats-new-for-performance-in-wpf-in-net-4)
- "We now use a cached copy of DispatcherSynchronizationContext instead of creating a new one each time. We found this to provide ~15% gain in Editor Scroll scenarios" (shows that per-scroll-event allocations are measurable in WPF scroll paths; historical). — [.NET 4 performance post](https://learn.microsoft.com/en-us/archive/blogs/jgoldb/whats-new-for-performance-in-wpf-in-net-4)
- .NET 7: "Remove closure/delegate allocation in ItemContainerGenerator". — [What's new for WPF in .NET 7](https://devblogs.microsoft.com/dotnet/wpf-on-dotnet-7/)

### Inferences
- Per scroll event the handler does, for each of N rows: `ItemContainerGenerator.ContainerFromIndex` (generator lookup), `ContentTemplate.FindName` (name-scope lookup in the template instance), `TranslatePoint` (walks the visual parent chain composing transforms, and may need up-to-date layout), then allocates a new `TranslateTransform`/`ScaleTransform` and assigns it (property change, Changed-handler churn, new composition resource on the render thread, garbage). `ScrollChanged` can fire several times per frame during wheel/touch scrolling, so this work is repeated without any visual benefit.
- Exact pattern replacing it: on `Loaded` (or `ItemContainerGenerator.StatusChanged == ContainersGenerated`) resolve each row's target element once and store it with its own unfrozen `TransformGroup { ScaleTransform, TranslateTransform }` assigned once as `RenderTransform`; cache each row's layout offset relative to the scroll content once and refresh only on `SizeChanged`/`LayoutUpdated`; on scroll compute positions arithmetically from `e.VerticalOffset` and set only `.Y`, `.ScaleX`, `.ScaleY` on the existing objects; coalesce by storing the latest offset in a field and applying it in a `CompositionTarget.Rendering` handler (subscribe while scrolling, unsubscribe when idle) so the work runs at most once per frame.
- Scale changes on rows that contain HighQuality bitmaps re-trigger CPU Fant resampling (see the BitmapScalingMode section) and re-tessellation of vector content; putting `CacheMode="BitmapCache"` on the transformed row (or restricting the effect to translate + opacity) turns each tick into a pure GPU quad transform.
- Opacity animations on a subtree with children require an intermediate surface per animated element per frame (not sourced); the same BitmapCache makes that a single textured quad.

### Gaps
- No source measures `TranslatePoint`, `FindName` or `ContainerFromIndex` cost; the claim that they are significant here is unverified and should be checked with a CPU profiler (they may be minor next to rendering cost).
- No official guidance found on throttling `ScrollChanged` with `CompositionTarget.Rendering`; it is a common practitioner pattern.

## CacheMode=BitmapCache: when it helps and when it hurts

### Takeaway
BitmapCache converts a complex, static subtree into one GPU texture, so translating, scaling, fading or applying effects above it costs a quad instead of re-tessellation; it is regenerated only when the subtree's structure/content or the cache settings change. It costs video memory, trades away some quality, breaks RenderOptions/TextOptions inheritance, and is limited to 2048 x 2048 in software mode.

### Cited Findings
- "cache the element and its subtree as a bitmap in video memory. This is useful when you need to animate, translate, or scale a UIElement as quickly as possible. This approach enables a tradeoff between performance and visual quality while content is cached." — [BitmapCache Class](https://learn.microsoft.com/en-us/dotnet/api/system.windows.media.bitmapcache)
- "Cache regeneration occurs only when the structure of the UIElement or its subtree changes, or when the CacheMode settings change. Setting the RenderAtScale or EnableClearType properties causes cache regeneration. Changes to the parent visual tree of the cached UIElement, such as transforms, scales, opacities, and effects, do not affect the cache." — [BitmapCache Class](https://learn.microsoft.com/en-us/dotnet/api/system.windows.media.bitmapcache)
- "The cache functions when hardware acceleration is not available. In this case, the bitmap is rendered in software, and the maximum bitmap dimensions are 2048 x 2048." — [BitmapCache Class](https://learn.microsoft.com/en-us/dotnet/api/system.windows.media.bitmapcache)
- "RenderOptions and TextOptions do not propagate through a cached element." `SnapsToDevicePixels` on the cache is needed for pixel-aligned content such as ClearType text; `EnableClearType` and `RenderAtScale` are the quality knobs. "Caching a control does not affect mouse-over behavior". — [BitmapCache Class](https://learn.microsoft.com/en-us/dotnet/api/system.windows.media.bitmapcache)
- Motivation and target scenarios: "allows primitives to be rendered as fast as the video card can draw a quad, moving the bottleneck from CPU primitive setup to GPU fill-rate"; "there can be some loss of visual quality"; scenarios: scaling/rotation of live controls, smooth scrolling of cached content, "Fast scaling and translation of Vector content". XAML: `<BitmapCache EnableClearType="true" RenderAtScale="4"/>`. — [.NET 4 performance post](https://learn.microsoft.com/en-us/archive/blogs/jgoldb/whats-new-for-performance-in-wpf-in-net-4)
- Related principle for brushes: where content and its use are static, not caching "conserves video memory". — [Optimizing Performance: 2D Graphics and Imaging](https://learn.microsoft.com/en-us/dotnet/desktop/wpf/advanced/optimizing-performance-2d-graphics-and-imaging)
- Mixed field reports: a developer reports no gain from BitmapCache when moving/resizing controls containing geometric figures (resizing invalidates the cache). (Snippet, anecdotal) — [SO: BitmapCache poor performance while resizing](https://kiwix.lema.org/stackoverflow.com_en_all_2023-11/questions/54604262/bitmapcache-poor-performance-while-resizing)

### Inferences
- Good candidates in this window: the vector illustration (about a dozen Béziers-heavy Paths that never change), each changelog row if rows are transformed/faded by the scroll handler, and the content under the animated BlurEffect. Each becomes a texture that scrolling merely translates.
- Bad candidates: anything whose content changes frequently (a cache that is regenerated every frame costs more than no cache), elements larger than the max texture size (2048 px in software; the whole scroll extent must not be cached as one element — cache per row or per illustration instead), and text you need razor-sharp at fractional DPI scales (set `SnapsToDevicePixels="True"`, `EnableClearType` as needed, or `RenderAtScale` = monitor DPI scale; at 150 % scaling the cache memory is 2.25x).
- Because RenderOptions do not propagate through a cache, `BitmapScalingMode="HighQuality"` set on an ancestor above the cached element stops applying to images inside it; re-declare it below the cache if still wanted.
- Memory estimate: a cached 800 x 600 DIP row at 150 % scale is 1200 x 900 px x 4 bytes = about 4.3 MB of video memory; a dozen such rows about 52 MB (arithmetic).

### Gaps
- A Stack Overflow answer surfaced only in a search summary claims "up to 15x the fps" from BitmapCache on many containers under a blur overlay; I could not pin down the URL, so it is not cited as a finding.
- Whether BitmapCache contents are re-rasterized when the cached element's own Opacity is animated (versus an ancestor's) was not verified.

### Inferences
- Nothing in the .NET 8/9/10 notes changes the cost model of the constructs in this window (image decode, Fant, VisualBrush mask, effects, layered windows); the rendering core is unchanged. - From background knowledge, not verified in this run: .NET 8 is an LTS release (November 2023) whose support window was scheduled to end in November 2026, which would make moving to .NET 10 (LTS, November 2025) advisable for servicing reasons independent of performance. ### Cross-cutting ranking for the changelog window (inference, not a cited finding)
Ordered by expected impact on this specific window; every item needs profiler confirmation.
1. Check the rendering tier first (`RenderCapability.Tier >> 16`, remote session, VM). If it is 0, effects and scaling run on the CPU and items 2-4 dominate everything.
2. `BlurEffect` on the whole ScrollViewer: attach only during the intro animation, set `Effect = null` afterwards, and cache the content beneath it; never leave it attached during scrolling.
3. `DropShadowEffect` BlurRadius 40-80 on panels containing live/scrolling content: move the shadow to an empty sibling element or a pre-rendered 9-slice image.
4. Images: decode to display size (`DecodePixelWidth` x DPI scale), separate small decodes for the 26x18 and 302x136 uses, `CacheOption=OnLoad` + `Freeze()` off the UI thread, re-save PNGs at 96 dpi; then drop `HighQuality` where the scale is near 1:1.
5. Replace `OpacityMask` + `VisualBrush` with a rounded `Border`/`Rectangle` filled by an `ImageBrush`, or a `RectangleGeometry` Clip.
6. Scroll handler: resolve elements once, mutate persistent transforms, coalesce to once per frame; avoid animating scale on rows containing Fant-scaled bitmaps or put `BitmapCache` on those rows.
7. Vector illustration: one frozen `DrawingImage` (or the existing Paths under one `CacheMode="BitmapCache"` parent).
8. Defer off-screen rows' heavy content (lazy image sources) rather than converting a dozen rows to a virtualizing panel.
9. Freeze shared Freezables (brushes, pens, text decorations, geometries); share FontFamily lists as resources.
10. Framework upgrade (.NET 10): unquantified font/XAML improvements; lowest confidence.
